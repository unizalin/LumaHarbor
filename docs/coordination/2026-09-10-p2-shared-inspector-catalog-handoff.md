### Behavior changes

1. **New, cross-platform**: Inspector search (filters `InspectorCatalog`'s 8 sections by field ID / synonym / title, tap-to-navigate), per-section favorite (device-local only, never synced), pin (suspends Smart Follow), Smart Follow (canvas tool mode → matching Inspector section, driven by the pre-existing `EditorSession.toolMode`/`EditorToolMode`, not a new selection concept), section reset, and domain reset (Adjust/Geometry/Local), each routed through `InspectorCatalog`'s pure `resetting`/`isNeutral` functions and `EditorSession.updateAdjustments(_:)` (same undo/autosave path every other panel edit already uses — reset is one undo entry, not a bypass).
2. **Bug fix, iPad-only, pre-existing**: iPad's Color submode declared `basic.temperature`/`basic.tint` in `PadAdjustSubmodeKinds.color` but `PadInspectorHost.adjustContent`'s `.color` case never mounted a panel for them — White Balance sliders were unreachable on iPad. Both the inlined and standalone `PadInspectorHost` now mount `BasicAdjustmentPanel(kinds: InspectorCatalog.section(.whiteBalance).adjustmentKinds)` in `.color`, matching Mac's `.color` `DisclosureGroup` (White Balance + HSL together).
3. **Deliberate, iPad-only field-placement move**: vibrance/saturation moved from iPad's Color submode to Light, to match Mac's Basic group (which already included them) — required by design spec §11.3 item 18 ("Mac 與 iPad 必須顯示相同 domain/section/field"). Before this, iPad's Color submode vocabulary *declared* vibrance/saturation but — same underlying gap as item 2 — never actually rendered a control for them, so this move has no user-visible regression on iPad (there was nothing there to lose); it only changes where they *first become reachable* (Light, alongside the other 6 tone sliders, via the shared `InspectorCatalog.section(.basic)`).

## Concerns and blockers

- **No manual/visual verification of the new UI this task.** Every new control (search field, star, pin, reset buttons) is proven present and wired by source-contract tests (string/structure assertions, matching this codebase's established pattern for SwiftUI code with no view-inspection library available), and the full test suite plus both platform builds pass. But no one has looked at the actual rendered layout — spacing, whether the new `catalogToolbar` row's 5 controls (search field + clear + favorite + pin + reset) fit legibly at the iPad's narrowest supported width (Compact, 320pt trailing-dock width unchanged), or whether the Mac `DisclosureGroup` header's added star+reset buttons crowd the existing title text at narrow Inspector widths (280pt, the documented minimum). Recommend a manual pass on both a real/Simulator iPad and Mac before this is treated as fully done, prioritizing: Compact iPad width, Mac Inspector at 280pt, VoiceOver reading order through the new controls, Dynamic Type at the largest accessibility size.
- **Standalone `PadInspectorHost.swift`/`PadToolRail.swift` remain a second, unbuilt copy.** These files are confirmed absent from `Apps/LumaHarborPad.xcodeproj`'s `PBXSourcesBuildPhase` (verified by `grep` — no match), so neither `xcodebuild` (the project's real device/Simulator build path) nor plain `swift build` (which can't even parse the `.swiftpm` manifest in this environment — `AppleProductTypes` isn't resolvable outside Xcode/Playgrounds) compiles them. They exist because two existing tests (`PadPresetContractTests.testPresetPlaceholderIsGone`, `CurveHistogramContractTests.testPadInfoDomainUsesTheSharedHistogramInsteadOfAPlaceholder`) source-parse this specific file and predate this task — deleting it would have broken passing tests outside this task's stated scope. This task applied the same two field-vocabulary fixes to the standalone copy that it applied to the inlined one (so it stops being a second source of the just-fixed WB/vibrance bug), but did **not** add search/favorite/pin/reset to it, since doing so would require plumbing `library`/`batchCoordinator` into a file with no current callers and no build path exercising it. Whoever next touches iPad's Inspector should decide once, deliberately, whether to (a) delete both orphaned files and the two tests that reference them, (b) add the missing dependency parameters and keep both copies in true lockstep, or (c) find out whether Swift Playgrounds/`.swiftpm` direct-open actually needs these files at all (if it doesn't, that settles it). This task did not make that call — it was explicitly out of scope for a container/catalog task and risked an unauthorized test-suite scope change.
- **`preconditionFailure` in `InspectorCatalog.section(_:)`**: unreachable given `allSections` is a compile-time literal covering every `InspectorSectionID` case (enforced by `testAllEightSectionsExist`), but a future engineer adding a 9th `InspectorSectionID` case without a matching `allSections` entry would crash at first `section(_:)` call, not at compile time. Acceptable tradeoff (Swift has no way to enforce dictionary-from-enum completeness at compile time without codegen), flagged for awareness only.
- **Real P0/P1 gaps carried forward unchanged**: `Scripts/run-mvp-acceptance.zsh` and real-device manual QA remain `NOT RUN` from before this task; this task did not attempt to close them (out of scope) and does not claim they are closed.
